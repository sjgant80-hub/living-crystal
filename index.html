Verified rules, decided by settling.

A library of routing rules, each of which passed a test on customer messages it had never seen, is written into the weights of a network that makes its decision by settling: relaxing into its lowest-energy state, with no program stepping through instructions. The network runs on an emulated analogue memory array, with the faults a real device has: few levels, noisy writes, noisy reads, drift, dead cells. The question: does the settled array make the same decision the software makes, and where does that stop being true?

What this is, and what it is not

It is

The first step of Simon's plan for the Living Crystal: a material whose arrangement is the program, which computes by settling, refuses what does not fit, and remembers as shape. This step takes a library of rules the estate has already proven on unseen data, writes them into a settling network, and checks that the settled network decides exactly what the software decides.

It is not a chip

There is no neuromorphic or memristor hardware in this build. Every device number comes from an emulator of an analogue crossbar, written to model the faults real devices have. A run on real silicon is the next step; it is named below and not done.

No electrical energy figure

The network's "energy" is a number the settle lowers, in Hopfield's sense, not electricity. Nothing here measures joules or watts. Speed is stated only as measured, on the machine that ran it.

Not alive, not aware

The plan's summit, a lattice whose settling models its own settling, is a direction. Everything past this step (grown or annealed materials, seeded copies, other geometries) is parked: not built here and not claimed.

Not a better router

The cast makes the library's decisions, no more and no fewer. Whether those decisions are right is the library's own claim, measured on its own page.

Words on this page

Verified pattern
A rule of the form "when these one or two words are in the message, send it to this team", kept only after it was right on a batch of messages it had never seen and again on a batch never used before. From the estate's pattern library (library three, routing).
The router
The library's own software: it sends a message to the team named by the first kept pattern, in library order, whose words are all present, and names every other team a firing pattern points to (a conflict).
Settling
Every unit looks at the weighted sum of its inputs and switches on or off; repeat until nothing changes. The final state is the answer. There is no instruction pointer: the weights are the program.
Energy
A single number for a state of the network, which every change made by the settle lowers here. It is a property of the arithmetic, not a power bill.
Crossbar
A grid of memory devices. Voltages on the rows, currents summed down the columns: one read gives every unit its input at once. Each weight is held as the conductance of a pair of devices (one for plus, one for minus).
Dead band
A column's sense amplifier only commits when the current is clearly positive or clearly negative. In between it does not resolve and holds its last answer. An array with any unresolved column has not settled.
Refused
The array did not settle within its step limit, or (on a damaged array) settled with two teams lit. A refusal hands the message to a person: the safe failure.
Settled wrong
The array settled cleanly to a decision the router would not make: the dangerous failure, because nothing flags it.
Sealed / sticky reading
Two ways to read the same settle. Sealed: refused only when it does not settle. Sticky (added before the held-out read): also refused when any column failed to resolve on any read along the way, as if each column had a latch that remembers it once wavered.
Levels, write noise, read noise
A device holds only a few distinct conductances; programming lands near, not on, the target; every read adds a little noise of its own.
Drift
Programmed conductances sag over time, and not all by the same amount. "Compensated" means the reader corrects for the average sag; it cannot correct for the differences between devices.
Stuck cells
Devices that are dead (stuck at zero) or shorted (stuck fully on) and ignore programming.
Held-out
Messages the network was never developed on, read once, after the code was frozen by its hash.

How it works

Four steps, then a real held-out message traced through them.

  1. The library. The routing library's kept patterns, copied byte for byte from the pattern-libraries repository at a pinned commit. Each names one or two words and one team.
  2. The cast. Each pattern becomes two units. Its pattern unit gets a strong positive weight from each of its words and a negative bias, so it can only switch on when all its words are present. Its first-pattern unit is driven by its own pattern unit and held down by the pattern unit of every earlier pattern that names a different team, so only the first firing pattern's team can light. First-pattern units of different teams hold each other down. Every weight is the same both ways, which is what gives the network an energy that the settle lowers.
  3. The array. Every weight is written into a pair of devices of an emulated crossbar: one row per input word, two bias rows, one row per unit; one column per unit. The emulator models few levels, write noise, stuck cells, drift and read noise.
  4. The settle. All units start off. Each step is one read of the whole array: every column's current is sensed at once, and each unit switches on, off, or (inside the dead band) holds. When every column has resolved and nothing changed, the array has settled; the team of the lit first-pattern unit is the decision, and the other teams of lit pattern units are the conflicts. If it has not settled within the step limit, it refuses.

What we found

Next: a real chip

Named here and not done. The emulator says what device a real run needs; only silicon can say whether a device meets it, and what a decision costs in electricity.

  1. A crossbar test chip or a memristor development board with per-device programming and read-back (write-verify).
  2. Cast the same library, program it, and run the same held-out set and the same sweep on silicon, reading every column's current.
  3. Measure energy per decision with a power meter: the first real energy figure this work would state.
  4. Answer the faults the emulator found first: drift spread (refresh, or a code that tolerates it) and stuck-on cells (test and remap after programming).

Adoption

Who this step is for today, and how a team would use it.

Device and chip teams

A way to put decisions you can audit onto analogue in-memory hardware, and a tolerance map that says what device quality keeps them exact: read your datasheet against Where it breaks.

Regulated operations

Edge and offline products

A decision made where the data is, with no network call and no model in the loop; it refuses rather than guesses when its hardware degrades past what it can carry.

Rolling it out

  1. Grow and verify the rules on your own messages with the pattern library (each rule kept only after unseen data agrees).
  2. Cast the library and run the check of every possible input: the cast must match the software on all of them before anything else.
  3. Place your device on the edge map (levels, write and read noise, drift spread, stuck cells); keep the sticky latch on so a wavering array refuses.
  4. Re-cast and re-check whenever the library changes. The check is a few minutes on a laptop.

White paper: verified rules on settling hardware

The problem

Settling hardware (analogue arrays that compute by relaxing to a low-energy state) is fast and frugal on paper, and it is usually given trained neural networks: millions of weights nobody can read, on devices that drift and fail in ways nobody can enumerate. Two unknowns multiply. You cannot say what the network should do on a given input, and you cannot say whether the device did it.

The approach

Remove the first unknown. Start from a library of rules that each passed a test on data they had never seen, and compile it into a network whose every weight is a rule's word, bias or priority. Because the library reads a small, fixed set of words, the whole input space is finite: the cast can be checked against the software on every possible input, not a sample. What is left is the second unknown, the device, and that can be swept fault by fault in a faithful emulator until it breaks.

The design choices that matter

  • Symmetric weights, so the network has an energy and settles (Hopfield, 1982).
  • Wide margins: every unit's field at a settled state sits half the largest weight away from its threshold.
  • A dead band in every sense amplifier, so a field too close to call holds the array unsettled instead of being rounded.
  • Priority by inhibition: an earlier rule of another team holds a later rule's first-pattern unit down, reproducing "first kept rule wins" with no ordering logic outside the array.

What it showed

Limits

One library, of routing rules with one or two words each. An emulator, not silicon; the device figures are assumptions swept across a grid, not a datasheet. No electrical energy measured. The cast reproduces the library's decisions; it inherits the library's mistakes.

Related work

J. J. Hopfield (1982), on networks with an energy that settle into stored states. Analogue in-memory computing with resistive and phase-change devices, which is where the device faults modelled here come from. The estate's settling ladder (settling-cell to chip-immune), whose recurring lesson this step meets again: a settle can erase the uncertainty that should have stopped it.

For business

In one breath: decision rules you can audit, proven to compute exactly the same on settling hardware as in software, with a map of how good the hardware must be and a fit-check that refuses rather than guesses when it is not.

Security and data protection

  • The decision is made on the device, from which words a message holds; no message leaves it and no model is called.
  • Every weight traces to a named rule and its exam record, so the decision path is inspectable end to end.
  • A wavering or faulty array refuses (with the sticky latch on) and hands the message to a person. Stuck-on cells are the exception the record names: they can produce a confident wrong answer, so test and remap after programming.
  • Over-driven input lines can forge a two-word rule; the settle does not catch this, so input drivers must clip at the rail.
  • UK GDPR: the rules read words, not identities, and run where the data already is. Your data protection officer still signs off the deployment.

Deployment and roll-out

This step runs today in an emulator and in this page, with no install. On hardware: cast, program with write-verify, check every input, deploy with the sticky latch, re-check on every library change. A real-chip pilot is the next step named above.
